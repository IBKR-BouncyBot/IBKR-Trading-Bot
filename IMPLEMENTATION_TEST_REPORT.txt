IMPLEMENTED FINDINGS

H-02 / H-03: A possibly transmitted order retains its exact OrderRef and known
broker IDs as SUBMISSION_UNKNOWN. The cycle persists MANUAL_REVIEW and stops
the current action batch, without automatic duplicate submission. Reconnect
alone does not clear this uncertainty. Definite pre-transmit failures retain
ordinary rollback. Cancellation requires exact reference and client identity.

H-04 / H-11 and related M-02 / M-05 paths: New subscriptions do not inherit
freshness from cached values or size-only updates. BUY decisions, settings
edits and partial-BUY supervision check independent price/bid/ask evidence.
Same-contract subscription replacement and lost-stream cleanup retire the
exact owned ticker/request mappings without disturbing unrelated streams.

H-05 / H-06 / H-07 / M-06: Recovered ordinary SELLs use live exact-quantity
handling. Fresh exact-account/contract holdings must cover reconciled app-owned
unsold quantity; unrelated extra holdings are allowed. Historical replaced-order
executions and commissions resolve through persisted identity and remain
idempotent. Working replacements are checked against remaining exposure.
Substantive partial-BUY rejection stops repeat while acquired shares continue
to be managed. Benign broker warnings do not stop a successful completed BUY.

H-08 / H-09 / M-04 / M-16: Protective preflight rollback uses the correct role.
Missing or uncertain configured protection becomes visible recovery state.
Replacement price/quantity and guards are checked before cancelling protection
and checked again before submission. Cancellation failure is reconciled and
made actionable. Repeated confirmed-cancellation polls are idempotent across
reloads and preserve the existing two-quote replacement confirmation. The GUI
distinguishes confirmed, missing, cancelling and unconfirmed protection.
Separate cancellation/submission cannot guarantee continuous protection.

H-10 / M-03: The configured spread ceiling applies independently of the
hard-risk master, including partial-BUY checks, and requires fresh valid book
evidence. Approximate weekday session hours cannot authorize an RTH-restricted
new order when authoritative session evidence is unavailable.

H-12: Entry and profit comparisons retain unrounded configured thresholds.
One representable floating-point step accommodates arithmetic boundary noise;
two-step shortfalls and tiny configured movements remain rejected. Display
rounding is unchanged. Normal-price simulation boundaries remain covered.

H-13 / H-14 / H-15 / M-18: Orders use the confirmed cycle account and contract.
Blank accounts require one unambiguous managed account for a new cycle;
exposed historical cycles require unambiguous owned broker evidence. A new
cycle cannot displace unresolved exposure. Recovery connections and exact
owned cancellation remain possible. Advanced Connect shares workflow gating.

Restore companion safeguard: Required original columns, primary keys and
declared foreign-key integrity are checked. Supported additive migrations are
exercised on a disposable consistent SQLite backup, leaving the candidate and
active database untouched. This is not validation of every stored value or
substitute for broker reconciliation.

PYTHON 3.14 MIGRATION

Project metadata and source launch/test/build helpers require standard
GIL-enabled CPython 3.14.x. Windows helpers prefer py -3.14 and verify the
actual interpreter before installing packages. Stale/incomplete environments
and the free-threaded build are rejected with explicit guidance. Ruff/Pyright
targets and dependency floors were updated. No unrelated runtime rewrite was
performed for the Python migration.

An existing virtual environment does not change Python version when the system
Python is upgraded. Keep the existing executable and database/backups; close
the app, rename the old environment, and create a new 3.14 environment. See
docs/V5_0_0_TRADING_SAFETY_AND_PYTHON314.md for exact commands and behavior
changes. Most dependency ranges have upper bounds; tzdata has a minimum only.
The requirements are not a tested deployment lockfile.

CHANGES AND REVIEW

- Completed capture files may contribute same-instrument pre/post-fill
  context even if auto-repeat assigns later ticks to the next cycle. This
  exception requires matching manifest/event cycle and instrument identity,
  fill metadata and valid time bounds. Unverified files retain strict cycle
  filtering. Wrong-instrument and out-of-window context remains excluded.
- Opening Cycle audit starts one read-only Python worker. It prepares decision
  text and reads captures once for both Timeline and Market capture. Widgets
  remain on the GUI thread; decisions are inserted/refitted in batches of up
  to 40 rows with a 6 ms work budget. Column autosizing runs once with a bounded
  sample. Closing cancels further work without waiting on the GUI thread.
- Timeline shows only nonblank before/after stage changes; the complete
  Decision events and raw audit records remain available.
- The disconnected Account box displays N/A when no account is known.
- Guessed U.S. RTH schedules and New York timezone substitutions are removed
  from the adapter and display. RTH uses IBKR ContractDetails liquidHours and
  timeZoneId, not price ticks. Missing/unusable evidence reports unavailable
  and cannot declare the session open. Valid published sessions, holidays,
  early closes, cached boundaries and the LSE continuous-session cap remain.

Separate reviews checked capture identity/time bounds, RTH behavior and
worker lifecycle. Review identified a queued-callback edge case following Qt
parent destruction; cancellation checks now cover those callbacks, with
regression tests. No additional blocking defect was found in the final review.

PENDING MARKET-DATA SUBSCRIPTION CORRECTION

Investigation of a reported connection/RTH symptom found a reproducible
market-data liveness regression in the earlier 5.0.0 subscription changes.
Nonblocking price polls replaced a pending fallback subscription before its
first callback. A deterministic broker double with a 300 ms initial response
and 100 ms polls reproduced 42 requests, 41 cancellations and zero delivered
ticks over two seconds. The 4.2.0 comparison received its first tick at 300 ms.
This establishes a source defect, not the cause of the user's current incident;
no diagnostic report from the failing installation was available.

The runtime fix is one condition in app/ib_adapter.py: a zero-wait poll retains
the existing pending fallback. It adds no wait to the broker cadence. Positive-
budget probes can still try other requests, and the single-active-subscription,
retired-request detachment and field-freshness protections remain. Pending or
cached data is not promoted to fresh evidence. Order and RTH paths are unchanged.

The same reproduction after correction makes two requests, one cancellation,
receives its first tick at 300 ms, and retains one live request. Three added
regressions cover pending generic/direct requests, slower initial responses
and positive-budget alternative probing. The new failure cases were exercised
against the previous predicate before the fix; no production price-selection
behavior was changed to satisfy their fixtures.
