BouncyBot v3.9.0 - Audit Diagnostic Coalescing and Live Guard Status
Implementation and Test Report
Date: 2026-08-06

1. Release basis

This release was implemented on top of the finalized BouncyBot v3.8.0 BUY
partial-fill-grace source tree. It advances the project to v3.9.0 and changes
only audit/diagnostic emission policy, live operator visibility for the current
Stage-3 SELL evidence condition, corresponding documentation, regression tests,
and release metadata.

The v3.8.0 strategy formulas, field-level market-data safety rules, two-update
Stage-3 confirmation requirement, pre-submit revalidation gates, order types,
quantity calculations, broker mutation paths, RTH decisions, ATR inputs, fill
reconciliation, risk limits, and watchdog recovery behavior are unchanged.

No SQLite table, column, index, migration, or persisted setting was added.
Existing v3.8.0 databases, cycles, orders, executions, settings, backups,
checkpoints, captures, and portable state remain compatible.

2. Implemented behavior

A generic in-memory diagnostic-condition coalescer now tracks persistent
operational conditions with stable keys and reason codes. Changing values such
as quote age, price, spread, timestamp, or reconnect attempt number remain in
structured context but no longer form the suppression identity.

Each condition can retain:

- first/latest observation timestamps;
- occurrence and per-reason counts;
- latest detailed message and structured context;
- observed maximum numeric metrics;
- immediate and periodic audit-emission counts; and
- the number of cadence observations actually suppressed from SQLite.

Depending on operational relevance, the audit sequence is bounded to an initial
condition event, delayed persistence summaries, and one recovery event. The
underlying safety condition is still evaluated on every controller cadence.
Coalescing affects only diagnostic persistence and presentation.

3. Stage-3 SELL quote evidence

The final-SELL guard now reports stable reason codes including incomplete,
crossed, stale, independently stale bid/ask, wide-spread, unavailable tracking,
missing distinct update, unavailable trigger, and trigger-not-reached states.

Routine cached/non-price callbacks remain GUI-only. A complete valid quote whose
executable bid is below the profit trigger is treated as ordinary waiting rather
than a warning. Invalid evidence is still immediate when it occurs near or above
the trigger, invalidates an accepted first confirmation, removes critical field
or upstream proof, or fails the final submission revalidation.

The Price Data Monitor continuously shows the current Stage-3 evidence state,
reason code, detailed explanation, executable bid, trigger, percentage distance,
confirmation state, observation count, and accurately calculated suppressed-row
count.

The complete v3.7.0/v3.8.0 SELL-safety boundary remains unchanged: independently
fresh bid and ask fields, complete positive non-crossed quote, configured spread
limit, executable bid confirmation, two distinct qualifying updates, durable-
intent revalidation, and broker-call revalidation.

4. Other coalesced diagnostics

- Reconnect attempts use one outage condition: an immediate WARN, an INFO
  persistence summary after one minute, WARN summaries every five minutes, and
  one INFO recovery event. Retry behavior remains every ten seconds.
- Normal unchanged native BUY/SELL trailing-order waits summarize as INFO no
  more often than every 15 minutes. Selected-price or raw-Last trigger anomalies
  remain immediately visible and receive bounded anomaly summaries.
- Repeated BUY preflight blockers are grouped per cycle with stable blocker reason codes.
  Expected ATR/RTH/session waits use informational 15-minute summaries; hard
  data, broker, and risk blockers use immediate WARN and one-/five-minute
  persistence cadence.
- Stage-3/Stage-4 close-before-RTH timing and settlement waits use the same
  condition model. Missing session-boundary proof remains an immediate warning.
- Critical order rejection, terminal partial fill, quantity mismatch,
  reconciliation uncertainty, storage/worker failure, failed durable
  submission, and ERROR/MANUAL_REVIEW transitions remain unthrottled.

5. Regression coverage

The focused v3.9.0 tests cover:

- changing Stage-3 age text retaining one stable condition identity;
- a 705-observation NBIS-shaped stale-ask sequence producing bounded events;
- exact suppressed-observation accounting;
- current GUI status for cached/non-price callbacks without SQLite flooding;
- immediate near-trigger invalid evidence and confirmation invalidation;
- all documented Stage-3 stable reason-code mappings;
- native-order normal-wait and anomaly cadences, including explicit anomaly
  recovery back to the ordinary INFO cadence;
- reconnect aggregation and one recovery event;
- expected and hard BUY-preflight escalation/recovery;
- close-before-RTH session-boundary coalescing and recovery; and
- Price Data Monitor rendering of current Stage-3 guard evidence.

Existing historical release, incident, recovery, order, storage, GUI, simulation,
and packaging regressions remain in the complete suite.

7. Tooling limitations

Ruff and Pyright were not installed in the offline Linux release environment and
are therefore not recorded as passing. The final Windows run_all_tests.bat gate
must still run both tools before a native executable is produced.

A native Windows/PyInstaller executable was not built in this environment. The
Windows smoke test should confirm the packaged GUI status display, reconnect
summaries, native trailing-order wait summaries, SQLite audit output, and normal
IB Gateway operation during an extended Stage-3 wait.

8. Operational boundary

The diagnostic coalescer is intentionally in memory. A process restart clears
its housekeeping state, so a still-active condition can create a new entry event
and starts a new bounded summary interval. Trading and recovery do not depend on
coalescer persistence. The emergency log, critical decision events, and all
broker/order safety paths remain independent of this diagnostic suppression.

BouncyBot v4.0.0 - ATR Close-Window Persistence Correction
========================================================
Same-version source rerelease. No application/package version increment.

BASELINE
Previous v4.0.0 source archive:
IBKR_Trading_Bot_4.0.0_ATR_Session_Memory_Order_Editing_Source.zip

The exact extracted baseline independently passed all 1,284 tests in 183.94s.

REQUEST AND SCOPE
Restrict persistent ATR checkpoint writes to the final five minutes of RTH,
the final session-close flush, and orderly application shutdown. The aim is to
retain the latest valid estimate for the next matching session, not to save it
once a minute throughout the entire trading day.

Only one runtime file changes: app/atr_memory.py.
One regression module is added: tests/test_v400_atr_close_persistence.py.
README, changelog, current ATR/release/database/test documentation and this report
are updated. Existing test files are unchanged.

Controller, GUI, strategy, models, adapter, storage, main.py, watchdog, lockfile,
order-edit policy, capture writer, order diagnostics and all other runtime
modules remain byte-identical to the preceding v4.0.0. GUI improvements and
next-order editing from the initial v4.0.0 are retained. Application metadata,
dependencies, Windows build scripts, LICENSE and image assets are unchanged.

IMPLEMENTED BEHAVIOR
1. ATR continues to calculate normally throughout RTH. Each valid, ready ATR
   estimate updates the in-memory candidate; ordinary intraday calculations do
   not write that candidate to SQLite.
2. During the recorded session's final 300 seconds, the dirty candidate can be
   persisted at most once per 60 seconds. The five-minute boundary is inclusive.
   The existing verified broker RTH session times determine this window, including
   early closes and timezone offsets. Five minutes is a saving window, NOT a new
   ATR lookback or averaging period.
3. At/on the first processing pass after the recorded session close, the latest
   dirty candidate receives a final save attempt, even if the previous save was
   less than one minute ago. This retains the most recent observed estimate rather
   than leaving only the estimate from the last periodic checkpoint.
4. An explicit orderly application-close flush still saves the latest valid
   candidate, even when the user exits earlier in the trading day. The controller's
   existing shutdown call is unchanged. Unchanged checkpoints are not rewritten.
5. Temporary RTH-status loss or an intraday identity/parameter change no longer
   forces a save outside the closing window. Actual elapsed session close can
   still be recognized from the previously validated candidate's recorded close.
   A direct move into the next session can flush the old candidate before reset.
6. Persistence failures keep the dirty candidate. Automatic retries are bounded
   to once per minute after the one immediate final-close attempt, including
   when status flaps; failures cannot cause a database write on every callback.
7. Stored estimates are revalidated before writes. A reused checkpoint is not
   relabelled as a fresh observation; incomplete warm-up does not replace it.

COMPATIBILITY AND SAFETY BOUNDARIES
- Existing atr_rth_seed_v1 records and v4.0.0 databases remain compatible. No
  schema, persisted-settings format or dependency change is introduced.
- Exact contract/currency/exchange/profile/ATR-period/bar-duration matching,
  ready-state checks, finite positive values, session provenance, future-time
  rejection and the seven-calendar-day age limit are unchanged.
- Current-session ATR replaces the starting estimate through the existing logic.
- No synthetic ticks, refreshed bid/ask/Last timestamps, historical-data requests,
  relaxed freshness/session guards or broker actions are introduced by saving.
- A first session without a valid saved checkpoint still needs normal warm-up.
- A sudden crash or power loss before the saving window can lose that day's
  unsaved intraday candidate. The previous valid disk checkpoint is retained.
  Orderly app-close saving requires the worker to reach shutdown and the database
  to accept the write; a dead/blocked process cannot guarantee it.
- A seed from an early orderly exit is the latest estimate observed before that
  exit, not a claim to contain the actual later RTH closing observation.
