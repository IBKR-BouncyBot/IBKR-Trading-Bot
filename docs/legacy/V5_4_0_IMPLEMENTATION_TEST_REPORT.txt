REVIEW DECISIONS AND IMPLEMENTED CHANGES

1. Deferred order/fill backups: accepted with full validation retained.
   Nine existing backup triggers now enqueue CREATE_DATABASE_BACKUP on the
   existing controller worker. Durable order intent and fill records are still
   committed synchronously before submission or subsequent strategy actions.
   Final BUY/SELL freshness, RTH, entry-window and other submission guards are
   retained. Submission backup reasons are now order_submission, since a
   queued copy is not guaranteed to exist before transmission.
   There is no additional thread or cadence change. The queue defers the copy
   until the current handler returns; copying and validation can still stall
   later broker/event-loop work. A backup captures the state when it runs,
   not the state at request time. An abnormal termination may prevent a queued
   copy from completing. Authoritative SQLite records remain synchronous;
   existing shutdown and resume checkpoint behavior remains in place.

2. Schema-aware startup backup: accepted with early compatibility rejection.
   Successful initialization stamps PRAGMA user_version=1. An existing legacy
   stamp 0 retains a best-effort pre-migration online backup; a current stamp 1
   avoids making that redundant startup copy on every open. Existing additive
   table/column/index checks still execute. No new application table or column
   is introduced. The stamp is written only after schema operations succeed.
   The supplied patch checked a future stamp only after migrations and then
   claimed compatibility. Review reproduced a version 2 file being changed.
   This release reads the stamp read-only and rejects newer schemas BEFORE
   backup/migration writes. It also rejects an unreadable stamp. Independent
   review reproduced a transient SQLite lock that otherwise let a failed read
   bypass the future guard; the corrected guard preserved the version 2 stamp
   and schema when the same actual lock experiment was repeated.
   DatabaseSchemaError inherits sqlite3.DatabaseError, preserving existing
   corruption/error handling. Corrupt or unreadable sources remain untouched,
   and early rejection does not create misleading partial backup files.

3. Default backup retention 20: accepted after successful validation only.
   Ordinary backups retain the full existing SQLite integrity, required
   schema/primary-key, foreign-key and disposable restore/migration checks.
   The proposed validate=False path was rejected: it allowed an invalid new
   copy to delete the last known-good recovery copy. This was reproduced with
   a synthetic orphaned order and a one-file retention limit.
   Unconditional startup pruning was also rejected. Retention runs only after
   a new backup passes full validation, preserving old copies on copy or
   validation failure. Excess existing files are not deleted just by opening
   the app. Deletion failures can leave more than 20 files. Retention reduces
   retained disk occupancy; it does not reduce bytes written by each full
   backup. The next successful rotation applies the 20-file default.

4. ATR seed age 24 elapsed hours: accepted as an intentional policy change.
   A saved estimate is eligible through exactly 24 elapsed UTC hours from its
   observation. Older estimates, including normal Friday-to-Monday gaps,
   expire and the existing warmup applies. Eligible same-session and adjacent
   weekday reuse remains. No exchange holiday calendar is guessed. ATR
   formulas, seed identity/profile/contract checks, broker-reported RTH gates,
   current quote checks, fresh-bar preference and checkpoint write cadence
   remain unchanged. The seed record format stays version 1.
   The supplied test changes removed MONDAY and changed the meaning of FRIDAY
   without updating the close-persistence module; they also mislabeled a
   Saturday timestamp as the next weekday and invalidated one bad-boundary
   fixture. These were corrected without removing the safety assertions.

The README no longer states that screenshots are old. Current documentation,
changelog, package/GUI/build version strings and release assertions are
synchronized to 5.4.0. The 5.3.0 GUI note/report are archived; the prior report is
byte-identical. The supplied README branding and all five Images/ PNGs remain.

MINIMAL RUNTIME SCOPE

Operational changes are confined to app/controller.py, app/storage.py and
app/atr_memory.py. app/gui.py changes only its three release-version strings.
All other app modules, main.py and requirements.txt remain byte-identical to
the final 5.3.0 source. Build/runtime scripts and pyproject.toml change only
version strings. Standard GIL-enabled CPython 3.14.x remains the supported
runtime. Broker cadence, command draining, backup validation implementation,
strategy formulas, order types, quantities, stop calculations and reconciliation
logic retain their existing implementations. The tighter seed-age policy can
intentionally delay ATR-dependent progress until fresh observations suffice.

WINDOWS TEST-CLEANUP CORRECTION

The supplied Windows CPython 3.14.6 log reports 1 failed, 1922 passed and
1 warning. The failure occurs when TemporaryDirectory removes state-2.sqlite
after test_all_normal_order_types_commit_intent_and_submit_before_copy.
The test's independent intent-reader connection used sqlite3's transaction
context manager, which does not close the connection. Windows then reports
WinError 32 when deleting the database while that handle is still open.

The test now uses contextlib.closing for that reader. Its original order-intent,
submission and backup-ordering assertions are unchanged. Independent review
confirmed the cause and that the other new storage tests already explicitly
close their readers. No application module, dependency, version string or
changelog changed for this correction.

Fresh verification on Linux CPython 3.12.14, with ResourceWarning treated as
an error:
- A lifetime probe retained all five reader objects, preventing garbage
  collection from hiding the leak. Before the fix all five were still usable
  after cleanup; after the fix all five were closed and rejected queries.
- All 18 cases in test_v540_deferred_backups and test_v540_storage_reliability
  passed. The changed test module compiled and git diff --check passed.
- Release reconstruction and archive hash checks were repeated after the fix.

The complete suite was not rerun for this test-only correction. Windows
CPython 3.14 and Ruff remain unavailable locally, so the corrected Windows
run_all_tests.bat result is still unverified. The uploaded log does not include
the warning details. Evidence is included as validation/test_cleanup_*.log.

INDEPENDENT REVIEW AND LIMITS

Independent source review covered the original patch and resulting implementation.
It found the transient schema-read guard bypass described above, reproduced it
using a real SQLite exclusive lock, and verified its correction. It separately
ran 37 unittest cases and 99 ATR fallback cases. No further concrete defect was
identified in the reviewed runtime changes after corrections.

Python 3.14, pytest/coverage, Ruff, Pyright, native PySide6/Qt, ib_async, PyInstaller
and Windows/PowerShell are unavailable on this host. A bounded attempt to install
pytest/Ruff found no matching distribution available. The required quality-tool
command exits nonzero because Ruff/Pyright are missing; it did NOT pass. No
fresh coverage percentage, target-platform build, native visual or live-broker
qualification is claimed. The Windows run_all_tests.bat and build remain the
supported target-environment gates. Runtime checks were not weakened.
